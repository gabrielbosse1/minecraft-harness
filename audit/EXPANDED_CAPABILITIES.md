# Zinc capability architecture and expanded audit — 2026-11-12

## Scope, decision and evidence

**Verdict:** an architecture and incremental offline implementation, not a completed autonomous Minecraft engineer. The earlier `FINAL_READINESS.md` is the unchanged historical baseline, not a current specification. Its 39 original scenes are reproduced verbatim below and individually reassessed; the seven new scenes follow. The original report's statements about PvP consent as a *model morality defect* are superseded by the user's explicit preference: **the model controls its social choices, including choosing to hit a player**. A morally surprising choice is not itself a software defect. Targeting the wrong entity, fabricated observations, spoofed identity, and unexpected control loss remain technical failures. This does not mean risk is absent; operators should choose appropriate server rules, isolation and participants. Do not infer consent from a username or automatically add a consent/friend-list gate. Unknown people remain neutral until evidence/context changes the model's judgment; self-defense must not depend on verified identity. This phase removes the blanket player-attack rule from both harness action prompts and removes the duel-only examples from the ZincAI schema. The smaller harness still uses legacy loose name-based targeting and does not acquire ZincAI’s explicit-player resolver. Server rules and model judgment may still affect behavior; neither model conduct nor PT-BR output is guaranteed.

No Minecraft server, SMP, model endpoint or destructive live experiment was started or contacted in this phase. Tests use mocks; the repository also has loopback HTTP test fixtures, not a Minecraft server. Research was retrieved 2026-11-12. Repository last-push dates are GitHub metadata, not proof of maintainability. The target uses patched 26.3 data, not verified server parity. All scene outcomes below are predictions. Never equate a passing mock with gameplay.

## Implemented increment

* `zincai/region_inspect.js` and `zincai/logic_test.js`: see the continuation section below for a paginated 3D snapshot and an explicitly abstract, model-facing Boolean tester added after the initial report.
* `zincai/block_inspect.js`: bounded read-only `inspect_block(x,y,z)`, at most eight blocks from the bot's position, safe integer coordinates, loaded block only, up to eight sanitized finite state properties (omissions labeled), dimension and explicit snapshot/no-connectivity label. No navigation, digging, sign editing, block entity, exact power inference, trace or world mutation. Missing properties and chunks are explicit. State is the client observation and can be stale.
* `zincai/api_wrapper.js`, `index.js`, `system_prompt.txt`: schema exposed in all modes, validated through existing tool parsing, dispatched and returned as informational result; prompt documents its limits. Model decides whether/what to inspect. The separately existing `src/` harness does not gain this tool. This adds one schema to each action call; no measured live token/latency cost.
* `zincai/skills.js`: gather reports resolved dig calls, requested calls and exact requested-name inventory net change, explicitly unattributed and excluding other drops/later pickup; caps search radius at 32. A resolved dig is not proof a block broke or an item was collected. `ok` still means at least one dig call resolved, **not quota fulfilled**; failed searches can still lack progress accounting; cancellation, drop entities, concurrency and tool-specific yield remain unsolved. An alias like `iron` is not `raw_iron`: its exact-name delta cannot establish yield. The world ownership gap is unchanged.
* Both harness player interaction prompts and the ZincAI tool description now give the model the social decision instead of imposing a duel/warning rule; name-based targeting is not authenticated identity. The smaller harness prompt also asks for PT-BR rather than replying in the user’s language; neither harness can guarantee language compliance. `zincai/README.md` documents the changed policy; the prompt tests were updated.
* `test/capabilities.test.js`: mock tests exercise state/facing, unloaded and out-of-range, schema exposure/argument validation to executor/result, and the misleading-mining regression. `test/audit2.test.js` updates the expected tool count; `package.json` adds the tests and syntax check. Earlier uncommitted improvements and their tests remain documented in `FINAL_READINESS.md`; no large dependency was installed.

## Architecture: implemented vs proposed

```text
IMPLEMENTED: packets -> Mineflayer loaded world/entities -> compact snapshots -> action/chat model
                               |          ^                      |       |
                  inspect_block / region  results <- schema -> executor   PT-BR instruction/filter
                      paginated states       abstract logic_test        |
                      (no trace)              tasks + skills <--- decision
                                                  |  ^
                          System1 immediate safety -> arbiter -> controls
                                JSON memory/place index; agenda only in RAM

PROPOSED, NOT BUILT: snapshot/crop + version + timestamps + unknown cells
       -> 3D block state nodes -> evidence-labelled directed connectivity/missing boundaries
       -> logical net/ports (unknown where ambiguous) -> module hierarchy/intent
       -> query, inspect, trace or candidate test vectors -> compact cited result
       -> richer abstract/sequential simulation OR separately validated target-engine oracle
       -> model hypothesis/decision -> permission-aware plan -> transaction executor -> verification
       -> durable project/objective journal with evidence, version and provenance
```

**Do not collapse layers.** Physical block states and geometry do not themselves prove a connection; dust slope, solid-block power, facing, delay, locking, analog strength, scheduled updates and quasi-connectivity all require version-specific rules. An evidence edge should carry source/destination, rule and rule version, observations/time/chunk completeness, direction, strength/delay if known, and confidence/unknown reason. A logical gate/module is a hypothesis until validated, not a diagnostic fact. Support feedback/SCCs and temporal behavior rather than forcing a DAG. Loaded-world boundary, block entities, orientation, updates and chunk unloads must propagate `unknown`, not false. A declarative combinational Boolean graph evaluator now exists, but no physical connectivity graph, physical trace, module recognition, circuit persistence, physical simulation or causal diagnosis is implemented.

**Physical vs logical:** target-engine simulation means running that exact Java version and relevant server settings with reproducible input and scheduled ticks, plus differential observations; even then unsupported features are explicit. A custom simulator is only a model until differential-tested. A Boolean graph simulator is an abstract functional tool: test vectors can disprove/specify a *logical abstraction*, not prove real dust attenuation, tick/update ordering, quasi-connectivity, block motion, inventory signal, or build correctness. Do not report a fault cause or coverage percentage without a demonstrable complete graph and counterexample.

## Engineering analysis and model/local boundary

The compact model interface should expose goals and targeted questions, not raw global worlds: `inspect_block`, paginated `inspect_region` and builder-mode `logic_test` exist as bounded tools. Proposed examples include `trace_signal(port, direction, budget)`, `inspect_module(id)`, `simulate_logic(project, vectors)` and `plan_operation(intent)`; these do not exist. Future results need stable IDs, evidence age, unloaded/ambiguous flags, bounded output and no guessed cause. The existing tools are stateless snapshots/tests, not persistent project storage. Long-lived state should live locally and be summarized, with explicit drill-down rather than flooding every model call.

### Functional circuit design workflow (proposal only)

Capture loaded bounded 3D state with dimension/version/time; scan boundaries and mark unknown. Generate directed physical-rule edges with evidence and reversible provenance, then logical ports/nets and candidate submodules. Maintain stable hierarchical project records with revision, source world and dimension, I/O definitions, assumptions, tests, component state, mapping and build status. Query by project/module/coordinate and retrieve only relevant summaries. A model may select test vectors or suggest a fix; an abstract evaluator checks specified Boolean behavior only. Compare predicted physical behavior with the exact target-engine recordings before attributing a physical cause. Trace workflow: inspect → narrow upstream/downstream → propose hypothesis → choose safe test → observe input/output with timestamps → compare → report uncertainty/counterexample. No blanket repair claim.

For synthesis, evaluate a restricted declarative HDL/DSL and pinned cell libraries, then placement/routing with clearances, direction, signal restoration, timing, chunk boundaries, terrain/material and survival-access constraints. Reject unresolved routes; never silently generate incorrect circuitry. Schematic export is an artifact, not a world update. Provide cost/material estimate, preview and model/operator decision before bounded build, then verify states and test behavior. PERSHING and Re-RedScript are research inputs, not adopted compilers.

### Prioritized milestones

1. **Now, offline foundations:** truthful observations, mining results, paginated local region snapshots and bounded combinational logic testing (implemented narrowly); evaluate all scenes; no claims of physical simulation.
2. **Trustworthy interactions:** stateful container/sign/block transactions, exact positions, interruption and partial-result accounting, ownership boundary configuration. Exit: unit/property/fault-injection tests, no unintended mutation on refusal.
3. **State/control:** versioned durable objective and action journal, shared resource leases, epoch checks and preemption/resume. Exit: restart/lag/replay tests, bounded prompt and no duplicated transaction in mock.
4. **Redstone evidence graph:** bounded capture, version-specific rules and unknown edges, graph drill-down. Exit: rule fixtures and Java-engine differential tests for every advertised mechanic; record coverage, never extrapolate.
5. **Logic/project tooling:** extend the existing stateless combinational tests with module hierarchy, sequential behavior, persisted projects and declarative compiler experiments in an isolated worker. Exit: counterexample tests, sandbox escape attempts and explicit non-physical labeling.
6. **Place/route and live validation:** cell library, layout constraints and world verification; only after operator approval, dedicated disposable-server scenarios below. Exit: measured physical behavior, version-specific repeatability and documented failures. No general-purpose SMP readiness claim follows automatically.

## Continuation: implemented 3D and abstract-logic foundations

The following changes are present in addition to the initial increment above; the reproduced historical baseline remains unchanged.

* `zincai/region_inspect.js`, wired in `api_wrapper.js`, `index.js` and `system_prompt.txt`: `inspect_region(x,y,z,radius,page)` reads a cube of radius 0–2 (up to 125 cells), four cells per response, with x varying fastest then y then z. Every corner must be inside the eight-block radius. A page reports coordinates, observed states, unloaded/failed cells, truncation and that snapshots are non-atomic; there is no region-wide loaded or consistency guarantee. A detailed block can be queried with `inspect_block`. The tool is read-only, offered in all ZincAI modes and does not infer any power connections. Page contents can change between calls.
* `zincai/logic_test.js`: `logic_test` is offered in builder mode; the prompt tells the model how to discover it via `set_mode`. It consumes a small **declarative, topologically ordered combinational Boolean graph**: 1–9 named inputs, up to 128 gates (`AND`, `OR`, `XOR`, `NOT`, `BUF`, `NAND`, `NOR`), 1–9 outputs, and 1–512 explicit bit-string vectors, or generated unsigned 1–4-bit adder vectors. All nested data, sizes, unique IDs, arity and dependencies are validated again in the executor; unknown signals and cycles are rejected. It executes only predefined Boolean operations, never generated JavaScript, shell commands or Minecraft actions. Bits follow declared port order. In the adder mode the order is A least-significant bit first, B least-significant bit first, carry-in; outputs are sum least-significant bit first then carry-out. A width-four adder produces all 512 combinations locally. For explicit vectors, the expected values are supplied by the caller, not independently proven. Each result gives observed vector matches, the number of distinct input combinations tried, and the first actual input/expected/actual mismatch when present. `ok` means the test ran, even if vectors disagree; read the mismatch count. The input-combination count is precisely computed and says nothing about physical circuit coverage.
* `test/logic.test.js`, `test/capabilities.test.js`, `test/audit2.test.js`, and `package.json`: cover all gate operations, a generated correct 4-bit adder, actual failing carry counterexample, repeated/partial vectors, invalid graphs and arities, oversized/bad inputs, builder-mode tool exposure and execution, 3D paging, unavailable chunks and bounds. `package.json` includes new syntax checks and tests.

This is **not** a redstone-engine simulator, event/tick model, feedback/sequential emulator, circuit extractor, compiler, HDL runtime, placement-and-route, project store or physical fault localization system. It cannot identify whether a redstone dust line is connected, whether a particular physical circuit implements the caller's graph, or whether an observed mismatch is caused by any particular block. It reports a discrepancy, not a causal diagnosis. The evaluator itself is in-process but bounded to fixed operations and bounded input sizes; it is not a general code-execution sandbox. No new dependencies, server or remote model were used. Sending a 20-gate adder graph can require a long tool call, and current model output-token limits may truncate it: no live model/API success has been verified. A persistent project store and incremental graph construction would reduce repeated calls but do not exist yet.

### Concrete tool example

A model in builder mode can test a half adder without calculating every output manually:

```json
{"inputs":["a","b"],"gates":[{"id":"sum","op":"XOR","inputs":["a","b"]},{"id":"carry","op":"AND","inputs":["a","b"]}],"outputs":["sum","carry"],"tests":[{"in_bits":"00","out_bits":"00"},{"in_bits":"01","out_bits":"10"},{"in_bits":"10","out_bits":"10"},{"in_bits":"11","out_bits":"01"}]}
```

The result is a test of **this graph against these supplied expectations only**. To test a physical machine, a separately validated extraction and physical simulator/oracle are still required. To test a full adder, add `cin`, compose gates and set `adder_width:1` instead of `tests`; for a four-bit ripple design use `adder_width:4` and nine input/five output signals in the order specified above.
