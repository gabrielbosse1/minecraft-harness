# Zinc pre-session readiness audit — 2026-11-12

## Verdict: **NO-GO**

Do **not** begin the proposed multi-hour autonomous session or expose the bot to an ordinary shared world on the strength of this audit. Two confirmed control/property gaps remain P0 for an unrestricted or unattended session: matching a resource type cannot distinguish natural material from a nearby structure, and `stop` does not guarantee that a pending builder/shelter operation has stopped issuing world-changing calls. The underlying method invocations were demonstrated in synthetic sessions; **no actual server-side block change was observed**. They are nevertheless concrete violations of the safety guarantees needed to leave the bot operating around valuable property.

**Scope clarification:** this audit does not require, propose or add an owner record for every item or block. Ordinary social and property decisions can use the model's context and judgment; server/world or coarse region protections and disposable fixtures are operational safeguards where an operator needs them. No new item-ownership database, mandatory friend list or PvP-consent gate is part of this work.

A **conditional, short, supervised smoke test** may be useful after explicit operator approval, but it is not a downgrade of the overall NO-GO. It requires a separate disposable world, verified server-enforced interaction and region restrictions, no valuable items or uninformed participants, an operator watching continuously, and an independent way to revoke permissions/disconnect the bot. Do not rely on explorer mode, `allowDigging=false`, a whitelist, or the bot's `stop` response as a property-safety boundary. The staged plan below specifies the limited scope and stop conditions. More involved or mutation tests require separate approval after the P0 risks are fixed or genuinely contained.

**Evidence boundary:** no Minecraft server, SMP or real model API was contacted during this audit, and no real model credential was needed for the checks. The full offline suite now passes **254/254**, but the initial suite was **243/244**, with an intermittently failing horde assertion. A model endpoint and the target server's login, version, physics and gameplay remain **unverified**. A passing mock is not evidence of live survival, correct social judgment, physical pickup, circuit behavior or world protection.

## 2. Integration trace: from state to effect and back

The relevant ZincAI path is:

```text
Minecraft packets -> Mineflayer loaded state / entities / inventories / chat
  -> ThreatSense + observation + place index + local System1 reflex
  -> action or chat snapshot, bounded recent results and lexical memory recall
  -> mode-specific native-tool payload -> endpoint response
  -> parse/coerce + offered-tool check + decision epoch check
  -> dispatcher -> task / survival / combat controls and direct Mineflayer calls
  -> result/event + updated observed state -> future model snapshot
```

1. **Observation.** `zincai/observe.js`, `threats.js` and `places.js` turn the loaded client state into brief self, inventory, player, mob and nearby-place summaries. `index.js:759` assembles them with agenda, reasons, remembered facts and recent results. These are bounded views, not the full world or ground truth. Richer semantic perception functions are not a general scene map on the normal action path.
2. **Local safety.** `system1.js` runs a roughly 200 ms local reflex without waiting for an LLM. `control.js` prioritizes movement lanes, while `custom_mineflayer/escape.js` estimates routes. The arbiter does not govern every hand, equip, dig, placement or window operation. Unknown players are not made hostile merely by proximity or a held sword; a recent attacker can become a threat.
3. **Context/memory.** Working memory defaults to five entries, short-term to ten minutes, ephemeral context to 30 seconds, and lexical recall to the top three. Long-term JSON is capped at 500 entries with low-importance/old eviction. `recallBlock` labels source/date and asks for verification, but model-written summaries, name-based `factsAbout` and preferences may be stale, mistaken or misattributed. Best-effort file writes can fail silently. Conversation, places and facts can persist; the agenda is session RAM containing runnable closures, not a durable task journal or lossless context compaction. Death clears the main agenda; reconnect rebuilds a session.
4. **Request and response.** `api_wrapper.js` defines 33 total action schemas. Explorer excludes `build`, `build_shape`, `logic_test` and `circuit_project` from the offered tools, but still offers mutators and `set_mode`; it is not an access-control mode. The client checks that a selected tool was offered, consumes the first call, requests `tool_choice: "required"` and `parallel_tool_calls: false`, retries some malformed/truncated answers and falls back to `auto` only for certain matching HTTP 400 errors. Action requests default to 256 output tokens, 20 seconds and two retries; chat defaults to 120 tokens and a shorter timeout. All 33 schemas compiled with temporary Ajv strict checking; provider acceptance is unknown. The runtime checks top-level arguments, but schema-invalid nested `build.grid` and `logic_test.gates` examples were accepted by `coerceAction`; the logic executor performs further validation, whereas other downstream handling differs.
5. **Actual action.** `index.js` discards an action decision when its decision/life epoch has changed, and the separate chat lane also drops stale replies on death/disposal. That protects decisions **before dispatch**, not a physical operation already awaiting equip, look, pathing or server confirmation. `ControlArbiter.useHand` serializes its own borrowers but returns `hand_busy` even to an urgent borrower, and several direct calls bypass it.
6. **Feedback.** `report()` keeps five results; the action prompt includes the most recent four. Informational messages are cut at 900 characters, others at 260. `gather` reports resolved dig calls and an exact-name net inventory delta, explicitly not attributable to its digs; `ok` can mean some progress rather than the requested quota. `logic_test` can return `ok` because the test ran even if vectors mismatch. `stop` now says it was requested, not that the world is quiescent. Inspect actual result text and independently compare world/inventory state before claiming success.

### Representative end-to-end evidence

- **Danger -> prompt -> reflex.** Before the patch, forcing a pathfinder `timeout` for a visible zombie 4 m away produced `threats: none`, a `shut in — cannot reach you` note and no flee in the simulated session. After the patch, `timeout`, `partial` and malformed statuses are unknown, the visible zombie remains a threat and the local survival lane flees. A separate closed-wall mock still puts a close hostile with `reachable:null` into `hidden` (without falsely calling it caged); it can therefore fail to trigger flee. A completed `noPath` is only evidence within the small search budget, radius and loaded-world assumptions, not a real proof of containment.
- **Decision -> mutation -> feedback.** The reproducible synthetic sequence pauses equip, issues `stop`, then releases equip. Gather no longer begins a new dig at that point. In contrast, build still calls mocked `placeBlock` after the stop result; shelter calls mocked jump/placement and then cleanup. The probe replaces the methods and establishes invocation/order, **not** actual blocks placed or removed. A separate allowlisted oak-log fixture receives a mocked `dig` while pathfinder `canDig` is false; its result says one dig call and zero exact inventory change. The fixture contains no ownership metadata and does not demonstrate destruction of a particular player's structure.
- **Death -> remembered place -> recovery.** Before this audit, `corpse_run` looked for the named `last death` in the block index and failed even though death saved it in the named-place index. A mock session now walks toward the saved point in the same dimension, refuses cross-dimension destinations instead of silently walking to matching coordinates, and reports only nearby observed stacks; actual dropped-item collection is not verified.

These examples show why a bot's wrong result need not be a reasoning failure: the model may have received an incorrect threat summary, an acknowledged stop before a pending placement, or incomplete/stale state. Capture all links in the chain before judging the model.

### Changes made in this audit

- `zincai/threats.js`: `success`/`noPath` are distinguished from partial, timeout and malformed results; a visibly closing melee hostile is not demoted solely by a cached negative path result. The separate occluded-unknown limitation above remains.
- `zincai/skills.js`: gather rechecks cancellation, task control and the target after awaited equip/look and before starting a dig. It does not abort an already-started dig or distinguish a natural resource from the same block in a structure. Death recovery uses the named-place index; same-coordinate walks to a different dimension are refused, `find` labels dimensions, and pickup/despawn are not claimed.
- `zincai/builder.js`, `api_wrapper.js`: shape parameters are finite bounded integers, with a 128 dimension maximum, shape-specific minimums, a 250,000-work bound and 32,768-block cap. Unknown parameters are refused. The advertised floor is `{w,d}` and box `{w,d,h}`, matching the existing generator; callers using the old misleading `{l,w}` description must update.
- `zincai/index.js`, `system_prompt.txt`, `api_wrapper.js`: stop feedback says cancellation was requested; the model is no longer promised guaranteed projectile dodging, optimal equipment, verified completion or safe build reruns. The prompt remains within its existing length test. These wording changes do not enforce safety.
- `test/pre-session-safety.test.js` adds ten offline regressions and is included in `npm test`; the existing prompt test now asserts the truthful caveats. `audit/repro/15-mutation-boundaries.js` and `16-threat-boundaries.js` preserve the synthetic diagnostics. `zincai/README.md` now lists the current tools and prominent safety limits.

## 4. Updated redstone capability — useful, but not a physical oracle

- `redstone_scan` reads a nearby radius 0–2 cube, returning a session snapshot ID, component inventory, unknown/unloaded counts and paginated coordinates. `redstone_component` examines a listed component's reported states and evidence-labeled neighboring relationships. Snapshots are non-atomic and stale; only four are retained per session. Observed dust geometry is **not proof of current power or a complete directed connection**. `inspect_block` and `inspect_region` are additional bounded read-only observations.
- In builder mode, `logic_test` evaluates a caller-supplied, bounded, acyclic **abstract Boolean** graph, not a world-extracted circuit. Offline tests include a four-bit adder over 512 vectors and a real logical counterexample. The meaning of `ok` is that evaluation ran; check matches/mismatches. A declared dependency cone is not a diagnosis of a physical fault.
- `circuit_project` persists up to 16 named abstract specifications/results and historical snapshot summaries; it can list/show/page graphs and rerun tests. It does not persist a full live physical graph or automatically resolve stale snapshots. Rescan and revalidate before relying on old evidence.
- Offline redstone tests passed **17/17**, including pagination, unknown state, executor dispatch, no modeled world mutation, abstract logic and project reopening. A later combined safety/redstone run passed **27/27**. This does not validate target-version block updates, propagation, timing, quasi-connectivity, extraction, physical layout or fault localization. Their absence is not a blocker for ordinary non-redstone gameplay.

## 7. Smallest useful staged server plan — future, only with approval

This is a **proposed** plan, not work already performed or permission to start. P0s keep the overall verdict NO-GO. A stage is eligible only after all earlier gates pass and the operator deliberately chooses to continue; a narrow pass does not certify the next stage or a multi-hour session.

### Prerequisites and common records

1. Create a separate **disposable** dedicated test world with a tested backup/reset. Pin the exact Java/server/protocol version and record server plugins, authentication and settings. Never point a first launch at the configured nonlocal default. Set `MC_HOST`, `MC_PORT`, `MC_AUTH`, `MC_VERSION`, model/base URL and a writable isolated `ZINC_DATA_DIR` deliberately; inject credentials privately, never into the report or logs. Confirm the server actually enforces identity and region rules appropriate for the deployment.
2. Prove from an independent account/server log that the bot cannot break/place blocks, change machines or access containers outside the disposable allowed area. Initially deny all mutation and PvP; where a later fixture needs a write, authorize only that fixture and reset afterward. Explorer mode and `behavior.allowDigging=false` do not provide this guarantee. A whitelist or an empty test inventory alone is not enough.
3. Have one observer in-game and one operator able to revoke permissions or disconnect/terminate the bot. Revocation/disconnection does not undo packets already accepted; inspect server state afterward. Do not rely on the model's `stop` acknowledgment. Use replaceable equipment, isolated participants and no valuable storage. Use an external time/budget cap and a kill switch.
4. Record UTC timestamps, code revision, config **without secrets**, world/version/auth, participant and fixture setup, prompt/observation if safely capturable, tool name/arguments and result, lane owner, actual server-side position/health/inventory/blocks/events, model latency/usage/retries and a short video. `metrics.jsonl` is best-effort and only written when usage is available; ordinary logs do not by themselves provide a complete raw prompt/response trace. Arrange approved, redacted capture before interpreting failures. Protect private chat and do not record authorization headers or API keys.
5. Before launch rerun `npm run check`, `node zincai/index.js --check`, `npm test` and the dummy-key dry run. Verify the specific final changes are deployed. Any failing or flaky prerequisite requires investigation rather than assuming a clean prior run applies.
